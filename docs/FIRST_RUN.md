# Первый запуск и будущий бэкенд

Сценарий: `SplashActivity` (три страницы знакомства) → `MainActivity` (проверка
доступа) → `AuthWelcomeActivity` → Яндекс ID → `AgreementActivity` → главная.
Знакомство показывается один раз; существующий флаг `isFirstLaunch` сохранён.
SOS и просмотр документов доступны до входа.

Компоненты `OnboardingScreen`, `AuthWelcomeScreen` и `ConsentScreen` независимы
от серверного API. При своей регистрации можно переиспользовать форму согласий.

## Согласия

Тексты из assets не изменены. Используются реальные файлы:

- agreement.txt — пользовательское соглашение;
- polkonf.txt — ознакомление с политикой;
- numtwo.txt — согласие для регистрации аккаунта;
- numthree.txt — согласие для функционала приложения;
- numfive.txt и numsix.txt — необязательные информационные и рекламные коммуникации.

numone.txt (договор) и numfour.txt (поддержка) остаются в каталоге документов;
согласия на эти отдельные цели на старте не собираются.

`ConsentRepository` атомарно сохраняет JSON в приватный каталог приложения
`files/consent_receipts/`: идентификатор записи, клиентское время, версию
приложения, идентификатор и SHA-256 каждого документа, вид подтверждения и
явное true/false для каждого выбора. Статус доставки — `local_only`.
Сетевой отправки и серверного подтверждения сейчас нет.

Пока у приложения нет проверенного сервером user ID, запись привязана к
отпечатку локальной сессии Яндекса. Токен в запись согласий не включается.
Новый токен/другая сессия требуют нового подтверждения. Это не серверная
идентификация пользователя и не криптографическая электронная подпись.

Старая единственная отметка `app_agreement.accepted` не содержит ни версии
документа, ни привязки к аккаунту, поэтому не заменяет новую запись. Существующий
пользователь увидит форму один раз после обновления, без сброса авторизации.
Изменение обязательного документа также потребует подтверждения новой версии.

## При подключении своей авторизации

Заменить `SessionRepository` на серверную сессию и устойчивый user ID,
предоставить серверные версии документов, передавать решения с receipt_id как
ключом идемпотентности. На сервере проверять аутентификацию, версии и обязательные
подтверждения; фиксировать серверное время. Локальному JSON нельзя доверять как
доказательству серверной авторизации. Статус доставки менять только после
подтверждения сервера. Настройки изменения/отзыва необязательных согласий также
потребуют отдельного пользовательского сценария и API.
